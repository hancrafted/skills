Quick win 1 of 4 · ★ Recommended

Fail when the Binding names a missing skill

binding.yml names a skill per DRIVE phase. main renamed one; the Binding kept the old name, and no check failed.

Analogy

A speed-dial button for a disconnected number: it looks fine in the list and rings nowhere, and you find out only when you need it.

Breaks down: a dead speed-dial fails on the call; a stale Binding fails silently, until an agent reaches for the skill.

Proposal Apply fail fast (+ check config against reality) so that a stale skill name fails the tests the day it goes stale.

Before

  1. ✓works: main renames a skill
  2. ✗fails: Binding keeps the old name
  3. ✗fails: all checks green
  4. ✗fails: found by hand at merge

After

  1. unchanged: main renames a skill
  2. unchanged: Binding keeps the old name
  3. ★changed: test fails, names the skill
  4. ✓works: fixed in the same PR
Evidence
  • EvidenceOn 2026-11-17 main renamed the installed skill to-decision-html to to-review. docs/drive/binding.yml still named the old skill and nothing failed. The Orchestrator found it by hand while merging main into feat/drive (merge 283abde8). Source: this brief, Orchestrator note.
  • UnknownHow long it would have stayed unnoticed.
  • EvidencePrior count 0: the first DRIVE Workflow.
Change and Enforcer

Proposal A fast-suite test reads docs/drive/binding.yml and fails for each skill it names that is not installed (.agents/skills/ or skills/). Alternative home: a drive setup check.

Enforcer: Test runner (npm test, in npm run verify and CI). Deterministic.

Cost, door, impact
Cost
15–30 min. Risk: a skill installed on only one machine fails the test elsewhere; the test reads the repo’s installed skills only.
Door
Two-way: delete the test.
Impact
Every future skill rename or removal. Renames already happened once in this Workflow.

Quick win 2 of 4

Make a failed wt:new leave nothing behind

wt:new failed mid-install and left its branch and folder behind; the rerun failed with “branch already exists”.

Analogy

Moving house with the old keys handed in and the boxes half unpacked: you can neither go back nor start over cleanly.

Breaks down: nothing is lost here; a rollback only removes what the command itself just made.

Proposal Apply all-or-nothing setup (+ idempotence) so that a failed wt:new leaves nothing and a rerun works.

Before

  1. ✓works: create branch
  2. ✗fails: install fails
  3. ✗fails: branch and folder stay
  4. ✗fails: rerun: “already exists”

After

  1. unchanged: create branch
  2. unchanged: install fails
  3. ★changed: remove what this run made
  4. ✓works: rerun starts clean
Evidence
  • EvidenceThe first wt:new -- decisions/drive created the branch, then ended in a Node stack trace. A rerun failed with “branch already exists”, and npm ci was rerun by hand in the half-made worktree. Source: decisions.md, observed failure 1.
  • UnknownWhat made the install fail, and how long the repair took.
  • EvidencePrior count 0.
Change and Enforcer

Proposal Wrap new in skills/worktree/scripts/worktree.ts so a failure removes only the worktree and branch this call created; a slow test injects an install failure and asserts both are gone.

Enforcer: Test runner: test:slow with an injected failure. Deterministic.

Cost, door, impact
Cost
15–30 min. More code in the worktree script; the stack trace itself stays unexplained.
Door
Two-way: revert the commit.
Impact
Every wt:new, which every Subagent runs once.

Quick win 3 of 4

Catch a main checkout switched to “bare”

Git’s core.bare=true means “no working files here”. It flipped to true in the main checkout mid-run, cause unknown.

Analogy

A shop sign flipped from “Open” to “Warehouse only”: the goods are inside, but every customer is turned away.

Breaks down: a sign is visible at a glance; this setting is invisible until a command fails.

Proposal Apply shift left (+ detect drift early) so that preflight catches it before any Subagent starts.

Before

  1. ✗fails: core.bare flips to true
  2. ✗fails: work goes on
  3. ✗fails: git fails oddly
  4. ✗fails: reset by hand

After

  1. unchanged: core.bare flips to true
  2. ★changed: preflight fails, names it
  3. ✓works: fixed before dispatch
Evidence
  • EvidenceMid-run, the main checkout’s git config was found set to core.bare=true; a Subagent reset it to false. Source: decisions.md, observed failure 2.
  • UnknownThe cause. The Orchestrator suspects a test leaked into the real repo; nothing confirms it. When it happened and what it cost: not recorded.
  • Evidenceskills/worktree/scripts/preflight.ts exists and checks nothing about core.bare today (searched).
Change and Enforcer

Proposal One check in npm run preflight that fails when git config core.bare is true in a checkout with working files.

Enforcer: New check in npm run preflight, with a test. Deterministic. It detects; it neither prevents the flip nor finds its cause.

Cost, door, impact
Cost
15–30 min. Low risk.
Door
Two-way: delete the check.
Impact
Every run that starts with preflight; the leak itself stays open.

Quick win 4 of 4 · Weak

End a hung slow-test run on its own

A test:slow run hung 7+ minutes despite the 60 s per-test limit. Its process kept the worktree busy, so wt:done refused.

Analogy

A kettle whose element switches off but whose pump keeps running: the safety cut-out exists, it just guards the wrong part.

Breaks down: we do not know which part hung; the analogy assumes it was outside the tests.

Proposal Apply bound every wait (+ clean up what you start) so that a hung run ends itself. Weak: cause unknown.

Before

  1. ✓works: tests stop at 60 s
  2. ✗fails: run hangs anyway
  3. ✗fails: process holds the worktree
  4. ✗fails: wt:done refuses

After

  1. unchanged: tests stop at 60 s
  2. unchanged: run hangs anyway
  3. ★changed: run limit kills the process tree
  4. ✓works: wt:done tears down
Evidence
  • EvidenceA Subagent left a hung vitest slow-test run (7+ minutes) in its worktree; wt:done refused to tear it down; the Orchestrator killed the process tree by hand. Source: decisions.md, observed failure 3.
  • EvidencePer-test limit already in place: vitest.slow.config.mts sets testTimeout: 60_000 since 2026-11-13 (commit fb0f3f8c). So the hang was not one slow test.
  • Evidencewt:done already refuses while a process runs in the worktree and offers --kill since 2026-10-20 (commit 1c2b9e32). The escape existed; it was not used.
  • UnknownWhere it hung: a hook, worker teardown, an open handle or watch mode. Without that, a fix guesses.
Change and Enforcer

Proposal Run test:slow under a wall-clock limit that kills its process tree and names the stage it was in. Cheaper alternative with no code: Subagent briefs finish with wt:done --kill.

Enforcer: Test runner wrapper, with a test that a deliberately hanging run is killed. Deterministic, but it bounds the symptom, not the cause.

Cost, door, impact
Cost
15–30 min. Risk: a limit that is too short kills a legitimate long run under load.
Door
Two-way: drop the wrapper.
Impact
Every test:slow run in a worktree; pre-push runs it too.

Architectural 1 of 3 · ★ Recommended

No new branch before the phase is announced

Twice the Operator stopped the Orchestrator to ask which phase it was in. The prose rule “announce each phase” cannot fail.

Analogy

A pilot’s callout before takeoff: the roll does not start until the whole cockpit has heard it.

Breaks down: the hook proves the callout was written, not that anyone read it.

Proposal Apply deterministic enforcement (+ make invalid states unrepresentable) so that wt:new runs only after the phase is announced.

Before

  1. ✗fails: Orchestrator runs wt:new
  2. ✗fails: no announcement
  3. ✗fails: Operator asks: “are we implementing?”

After

  1. ★changed: drive status announces, writes a marker
  2. ★changed: hook: wt:new needs the marker
  3. ✓works: Operator reads, not asks
Evidence
  • EvidenceThe Operator stopped wt:new -- decisions/drive: “are we starting to implement? or is this prep work? are we already on a new integration branch?”. Source: decisions.md, Corrections; learnings.md.
  • EvidenceThe Operator asked “can this session run until end or does it require a human?” and for a guide to reviewing. Same source.
  • EvidenceReview round Q46 added the prose rule: announce the phase on every start or resume. Guidance only; no check fails.
  • UnknownMinutes lost per interruption.
  • EvidencePrior count 1 (entered in learnings.md this Workflow, proposed).
Change and Enforcer

Proposal A drive status command that prints the phase, the branch state that follows and the Operator’s stops, and writes a dated marker; a PreToolUse hook on wt:new requires a fresh marker.

Enforcer: Hook (new) plus a test for drive status. Deterministic. Over the prose rule it adds a failure state.

Cost, door, impact
Cost
One ticket: a command, a hook and tests. Friction on every wt:new.
Door
Two-way: remove the hook; the marker stays harmless.
Impact
Every DRIVE step that creates a branch; the Operator’s two recorded interruptions.

Architectural 2 of 3

Keep a Subagent working until its branch is merged

Twice a Subagent stopped (“waiting on monitor”) before merging its Task branch, and needed a nudge to finish.

Analogy

A cashier who cannot clock out until the till is counted and handed over.

Breaks down: a Subagent with a real question must still be able to stop; the check needs an escape.

Proposal Apply definition of done as a machine check (+ verify, don’t trust) so that a Subagent cannot stop with its branch unmerged.

Before

  1. ✗fails: Subagent stops early
  2. ✗fails: branch unmerged
  3. ✗fails: Orchestrator nudges it

After

  1. unchanged: Subagent tries to stop
  2. ★changed: hook blocks: not merged
  3. ✓works: merges, then stops
Evidence
  • EvidenceTwice, a Subagent stopped before committing and merging and needed a SendMessage to finish the brief’s last steps. Source: decisions.md, observed failure 4.
  • UnknownWhich Subagents, and the time lost.
  • EvidencePrior count 0.
Change and Enforcer

Proposal A SubagentStop hook that checks the Task branch is merged into the Integration branch, with a way out when the Subagent reports a real blocker.

Enforcer: Hook (new SubagentStop), tested. Deterministic.

Cost, door, impact
Cost
One ticket. Risk: a loop when the Subagent cannot finish; the escape is part of the work.
Door
Two-way: remove the hook.
Impact
Every Subagent in every Workflow.

Architectural 3 of 3

Analogy

Booking a meeting room: check the calendar before inviting, not after two groups walk in.

Breaks down: tickets declare the files they expect; an undeclared edit slips through.

Proposal Apply shift left (+ isolation) so that overlaps surface at dispatch, not at merge.

Before

  1. ✓works: #667 and #668 run in parallel
  2. ✗fails: both edit learnings.md
  3. ✗fails: hand relay, then a conflict

After

  1. ★changed: tickets declare their files
  2. ★changed: dispatch refuses the overlap
  3. ✓works: run in order
Evidence
  • EvidenceParallel text tickets (#667, #668) and fix Subagents shared learnings.md and binding.yml; the Orchestrator relayed rules by SendMessage and one sync conflicted. Source: decisions.md, observed failure 7.
  • UnknownTime the relay and the conflict cost.
  • EvidencePrior count 0.
Change and Enforcer

Proposal A dispatch check that fails when two parallel tickets declare the same file.

Enforcer: New check in dispatch, tested. Deterministic, for declared files only.

Cost, door, impact
Cost
One ticket. Relies on tickets declaring their files.
Door
Two-way: remove the check.
Impact
