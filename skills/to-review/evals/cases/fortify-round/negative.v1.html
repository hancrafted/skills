Quick win: which one failure mode do we harden now?

Pick one 15 to 30 minute fix that a Subagent merges before cleanup, or pick none.

Two-way door, 15 to 30 min each. Fidelity: diagram: bars of observed incidents are enough to rank three narrow fixes.

Hung slow test (recommended)

  • Does: a timeout turns a hang into a failing test.
  • Benefit: no manual process-tree kill; `wt:done` can finish.
  • Cost: a slow-but-fine test may need a longer timeout.

Recommended: the clearest cause and the cheapest fix, and every Workflow runs slow tests.

Failure mode. A hung `test:slow` run keeps a worktree alive and `wt:done` refuses to tear it down.

Evidence: decisions.md observed failure 3: vitest hung 7+ minutes, the Orchestrator killed the process tree by hand. Correction: none.

Enforcer: test-runner `test:slow` with a test and hook timeout set in the slow vitest config, so a hang fails instead of waits (deterministic).

Prior count 0, new.

Half-made worktree

  • Does: `wt:new` removes what it created when a step fails.
  • Benefit: a rerun works at once.
  • Cost: rollback code to maintain; the cause of the stack trace stays unknown.

Failure mode. A failed `wt:new` leaves its branch behind, so the rerun fails with "branch already exists".

Evidence: observed failure 1: Node stack trace after the branch was created, `npm ci` rerun by hand.

Enforcer: test-runner `test:slow` with an injected install failure that asserts branch and folder are gone (deterministic).

Prior count 0, new.

core.bare flipped

  • Does: preflight fails loudly when the flag flips.
  • Benefit: catches it at once instead of mid-run.
  • Cost: detects, never prevents; finding the leaking test is separate work.

Failure mode. The main checkout's git config reads `core.bare=true`.

Evidence: observed failure 2: found set mid-run and reset by a Subagent; cause unknown, a leaking test is suspected.

Enforcer: new check in `npm run preflight` and before `wt:done`: `core.bare` is false in the main checkout (deterministic).

Prior count 0, new.

Architectural: which one ticket joins the tracker as the open `fortify` ticket?

Pick one ticket-sized hardening, or pick none. There is no open `fortify` ticket to replace or wait behind.

Two-way door for the ticket, a ticket of work each. Fidelity: diagram: incident counts and an Enforcer per option are enough to choose a ticket.

Phase and branch announcement (recommended)

  • Does: `drive status` states the phase; the hook blocks a branch-creating step without it.
  • Benefit: the Operator is never surprised by a step.
  • Cost: the hook checks that a marker exists, not that the Orchestrator read it.

Recommended: the only failure the Operator corrected twice, and it is the Operator who pays for it.

Failure mode. The Orchestrator starts a step without naming its DRIVE phase, the branch state that follows, or the Operator's decision points.

Evidence: two Operator corrections in decisions.md (stopped `wt:new` "are we starting to implement?"; "can this session run until end or does it require a human?" and a review guide). Now in learnings.md.

Enforcer: new hook on `wt:new` that requires a fresh phase marker written by a new `drive status` command, which prints phase, next branch state and Operator decision points (deterministic; `drive status` is tested).

Prior count 0 before this page; entered in learnings.md at count 1, proposed.

Subagent stops before merge

  • Does: a stop with unmerged work is refused and the Subagent told why.
  • Benefit: no relay messages from the Orchestrator.
  • Cost: a hook in each harness; a legitimately blocked Subagent needs an escape.

Failure mode. A Subagent ends its turn with its Task branch uncommitted or unmerged.

Evidence: observed failure 4: twice a Subagent stopped "waiting on monitor" and needed a SendMessage to finish the brief's last steps.

Enforcer: new SubagentStop hook running a tested `drive worktree verify-done`: tree clean and Task branch an ancestor of the Integration branch (deterministic).

Prior count 0, new.

Parallel tickets share files

  • Does: overlapping tickets run in sequence or merge into one.
  • Benefit: no conflicting sync, no relays.
  • Cost: tickets must declare their files, which they may get wrong.

Failure mode. Two parallel tickets edit the same file, so one sync conflicts.

Evidence: observed failure 7: #667 and #668 and fix Subagents shared `learnings.md` and `binding.yml`; rules relayed by SendMessage, one sync conflicted.

Enforcer: new check in dispatch that fails when two tickets declare an overlapping file, tested (deterministic; relies on declared files).

Prior count 0, new.
