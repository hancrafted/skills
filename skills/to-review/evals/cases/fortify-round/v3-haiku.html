Quick win: which one failure do we harden now?

Pick one for quick win

Recommended: QW-4. It is the cheapest deterministic check, and it fails on the next rename. QW-1 treats a symptom.

QW-1Stop a leftover process at teardown

A test left a process running, so wt:done refused to remove the worktree.

Analogy

A kettle with no auto-off: it keeps running after the job, and the next step waits until someone finds it. Where it breaks down: a kettle only wastes power; here the leftover process blocks the next step.

Proposal: Apply bounded teardown (+ fail fast) so that wt:done stops the leftover process.

Evidence

What happened: in this Workflow a Subagent left a vitest slow-test run going for 7+ minutes in its worktree; wt:done refused to remove it, and the Orchestrator killed the process tree by hand. Source: observed failure 3 in decisions.md, an Orchestrator note, not a measurement. Prior count 0.

Correction since round 1: a per-test limit already exists: vitest.slow.config.mts line 53 sets testTimeout to 60_000 (since 2026-11-13), and the hang happened anyway. So a timeout did not address this. The lever is the leftover process.

Unknown: which test hung, and why the process outlived it.

Weak point, stated plainly: this treats the symptom. The hung test stays unexplained.

The change and its Enforcer

wt:done lists processes whose working directory sits in the worktree, stops them, then tears the worktree down. A test starts a worktree with a live child and asserts that teardown succeeds.

Enforcer: Test in the wt:done suite (deterministic).

Cost, door and impact

About 15 to 30 minutes of one Subagent (agent estimate). Door: two-way, revert the commit. Risk: it may stop a process a person started in that worktree.

Impact: Removes the wait and the manual kill. It does not stop the hang itself.

QW-2Undo wt:new when it fails

A failed npm ci left the new branch behind, so the rerun said "branch already exists".

Analogy

Moving house with the boxes half unpacked: you cannot go back and cannot start over cleanly. Where it breaks down: nothing is lost; the rollback removes only what this command created.

Proposal: Apply all-or-nothing setup so that a failed wt:new leaves nothing behind.

Evidence

What happened: the first wt:new -- decisions/drive created the branch, then ended in a Node stack trace. The rerun failed, and npm ci had to be run by hand in the half-made worktree. Source: observed failure 1 in decisions.md. Prior count 0.

Unknown: what made the install fail, and the minutes it cost.

The change and its Enforcer

If any later step fails, wt:new removes the branch and folder this call created. A slow test injects an install failure and asserts that no branch or folder remains.

Enforcer: Test in test:slow with an injected failure (deterministic).

Cost, door and impact

About 15 to 30 minutes (agent estimate). Rollback is more code to keep. Door: two-way, revert the commit.

Impact: A failed install no longer needs manual cleanup. The stack trace itself stays unexplained.

Comment on QW-2

QW-3Warn when core.bare flips

The main checkout had core.bare set to true; git refused ordinary commands and nothing warned.

Analogy

A shop sign flipped to "Warehouse only": goods inside, customers turned away, and nobody changed the shop on purpose. Where it breaks down: a flipped sign is visible at a glance; this setting is invisible until a command fails.

Proposal: Apply shift left (+ detect drift early) so that preflight reports a flipped core.bare.

Evidence

What happened: mid-run, the main checkout had core.bare=true, and a Subagent reset it to false. Source: observed failure 2 in decisions.md. Prior count 0.

Unknown: the cause. The Orchestrator suspects a test leaked into the real repo; nothing confirms it. When it happened and what it cost: not recorded.

The change and its Enforcer

npm run preflight fails when core.bare is true in a checkout that has working files.

Enforcer: New check in npm run preflight (deterministic).

Cost, door and impact

About 15 to 30 minutes (agent estimate). Door: two-way, delete the check. Risk: low, and it does not fix the root cause.

Impact: Detects the drift early. It does not prevent it or find its cause.

QW-4Fail on a stale BindingRecommended

main renamed a skill, but binding.yml kept the old name. Nothing failed; the Orchestrator found it by hand.

Analogy

A speed-dial button for a disconnected number: it looks fine in the list and rings nowhere. Where it breaks down: a dead speed-dial fails on the call; a stale Binding fails silently, which is worse.

Proposal: Apply fail fast (+ validate references) so that a stale skill name fails at the rename.

Evidence

What happened: on 2026-11-17 main renamed the installed skill to-decision-html to to-review. binding.yml still named the old skill, and nothing failed. The Orchestrator found it by hand while merging main into feat/drive (merge 283abde8). Source: this session, Orchestrator.

Unknown: how long it would have stayed unnoticed.

The change and its Enforcer

A test, or a drive setup check, fails when a skill named in the Binding is not installed.

Enforcer: Test or drive setup check (deterministic).

Cost, door and impact

About 15 to 30 minutes (agent estimate). Risk: a skill installed on only some machines fails there. Door: two-way, delete the test.

Impact: Catches every stale skill name the same way, at the rename.

Architectural: which one ticket becomes the open fortify ticket?

Pick one for architectural

Recommended: AR-1. It is the failure the Operator corrected twice, and a mechanical check adds the failure state that the existing prose rule lacks.

AR-1Block wt:new until the phase is announcedRecommended

The Orchestrator skipped naming its phase, and the Operator stopped it twice. Only a prose rule exists.

Analogy

A pilot's checklist: takeoff waits for the callout. Where it breaks down: a checklist can be ticked without reading it; the hook proves only that the callout was written.

Proposal: Apply invalid states unrepresentable (+ deterministic enforcement) so that wt:new needs a fresh marker.

Evidence

What happened: two Operator corrections. The Operator stopped wt:new -- decisions/drive and asked "are we starting to implement?"; later asked whether the session could run to the end. Source: Corrections in decisions.md, verbatim in learnings.md. Prior count 1, status proposed.

Prose rule: the review round added "announce each phase on every start or resume" (Q46). No check fails when it is skipped.

Unknown: minutes lost to each interruption.

The change and its Enforcer

A drive status command, and a PreToolUse hook on wt:new that requires its fresh marker. What a check adds over prose: prose has no failure state; a missing marker does.

Enforcer: New hook, plus tests for drive status (deterministic).

Cost, door and impact

One ticket: a command, a hook and tests. Risk: a hook adds friction to every wt:new, and it checks that the marker exists, not that it was read. Door: two-way, remove the hook.

Impact: Targets the failure the Operator corrected twice.

Comment on AR-1

AR-2Stop a Subagent before merge

Twice a Subagent stopped before merging its branch, and needed a message to finish.

Analogy

A shift-end check: the cashier cannot clock out until the till is counted. Where it breaks down: a Subagent that asks a real question must still be allowed to stop.

Proposal: Apply definition of done as a machine check so that a Subagent cannot stop unmerged.

Evidence

What happened: twice, a Subagent stopped before committing and merging, and needed a SendMessage from the Orchestrator. Source: observed failure 4 in decisions.md. Prior count 0.

Unknown: which Subagents, and the time lost.

The change and its Enforcer

A SubagentStop hook checks that the Task branch is merged into the Integration branch, with a way out when the Subagent reports a real blocker.

Enforcer: New SubagentStop hook, tested (deterministic).

Cost, door and impact

One ticket. Risk: a loop if the Subagent cannot finish; the escape is part of the work. Door: two-way, remove the hook.

Impact: Removes the message round trip.

Comment on AR-2

AR-3Refuse overlapping parallel tickets

Two parallel tickets both edited learnings.md, and one merge conflicted.

Analogy

Booking meeting rooms: you check the calendar before inviting, not after two groups walk into one room. Where it breaks down: a ticket that edits an undeclared file is not caught.

Proposal: Apply shift left (+ declared ownership) so that overlaps are refused at dispatch.

Evidence

What happened: parallel text tickets #667 and #668, and fix Subagents, shared learnings.md and binding.yml. The Orchestrator relayed rules by SendMessage, and one sync conflicted. Source: observed failure 7 in decisions.md. Prior count 0.

Unknown: how much the relay and the conflict cost.

The change and its Enforcer

A check in dispatch fails when two parallel tickets declare the same file.

Enforcer: New check in dispatch, tested (deterministic).

Cost, door and impact

One ticket. Relies on tickets declaring their files honestly. Door: two-way, remove the check.

Impact: Finds the conflict at planning time, not at merge.
